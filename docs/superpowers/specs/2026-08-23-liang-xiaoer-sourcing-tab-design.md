# 粮小二第三 Tab「寻源任务」设计规格（DAG 编排版）

> 日期：2026-08-23
> 状态：已确认
> 范围：粮小二「寻源任务」Tab，将寻源流程做成可视化 DAG 工作流。用户自然语言下达需求，粮小二按 DAG 逐步执行、实时展示进度与中间产物，最终产出主推/备选/淘汰/待核验，并可沉淀为任务、交接运小二。不涉及供应方（该 Tab 移除）、历史记录 Tab。

---

## 1. 设计目标与真实痛点

粮小二是「寻源 Agent」，但现有「候选对比」是一次性算出结果的静态视图，用户看不到 Agent「做了哪些步骤、每一步得到什么」。采购员对 AI 出结论的最大不信任，正是「结论是怎么来的」。

「寻源任务」Tab 要回答：**让用户看着粮小二一步步跑完寻源流程，每一步都有产出、可解释、可追溯。**

真实痛点：

- AI 出主推/备选是黑箱，采购员不知道中间做了什么过滤、排除了谁、为什么。
- 自然语言需求到结论之间没有可观察的中间过程。
- 采购结论缺少「沉淀为任务、交接下游小二」的收口。

成功标准：

- 自然语言一句话触发，DAG 节点逐个点亮，用户能看到执行到哪一步。
- 每一步产出可复现的中间结果，最终主推/备选/淘汰/待核验与「候选对比」的确定性结果一致。
- 全程确定性计算，不接 LLM、不翻车。
- 结论可沉淀为任务、可交接运小二（结构化 mock）。

---

## 2. 已确认的核心决策

1. **DAG 编排可视化**：寻源流程拆成有向无环图节点，用户可见每一步。
2. **确定性执行引擎**：自然语言用 `parseNeed` 确定性提取，DAG 节点执行即 `compareListings` 的分解；毫秒级纯函数 + 前端定时器逐步揭示，制造「Agent 在跑」的编排感。不接 LLM。
3. **自然语言触发**：顶部输入框描述需求 → 自动跑完整 DAG。
4. **收口落库**：DAG 跑完展示结论，用户显式「保存为任务」落库；已保存任务可「交接运小二」生成结构化摘要。
5. **供应方 Tab 移除**：`agents.ts` 中粮小二 tabs 改为 `["找粮源", "候选对比", "寻源任务", "历史记录"]`，寻源任务接 index 2（第三位）。
6. **与候选对比并存**：候选对比是「轻量即时对比」，寻源任务是「正式编排执行 + 沉淀」。两者都出主推/备选但不合并。

## 3. 页面定位与 Tab 切分

| Tab | 职责 | 核心内容 |
|---|---|---|
| 找粮源 | 逛 | 市场浏览 + 筛选 + 加入候选 |
| 候选对比 | 比和定（轻量即时） | 并排对比 + 主推/备选/淘汰/待核验 |
| **寻源任务** | **跑和沉淀（编排执行）** | **DAG 工作流 + 进度可视化 + 保存/交接** |
| 历史记录 | 回看 | 历史任务/方案（不在本文档范围） |

## 4. DAG 结构

### 4.1 节点（8 个，含分支与汇合）

```text
①理解需求 → ②读取粮源 → ③硬条件过滤 ─┬─通过─→ ④排序比较 → ⑤主推/备选 ──┐
                                      └─淘汰─→ ⑥淘汰归因 ────────────────┤
                                                                         ▼
                                                         ⑦待核验清单 → ⑧沉淀任务
```

### 4.2 节点职责与中间产物

| 节点 | 职责 | 底层函数 | 中间产物（done 时在产出面板展示） |
|---|---|---|---|
| ① 理解需求 | 自然语言提取条件 | `parseNeed` | 条件卡：品种/数量/等级/年份/时间/预算 |
| ② 读取粮源 | 加载演示粮源 | `fetchListings` | 「已加载 N 笔粮源」 |
| ③ 硬条件过滤 | 逐条硬条件检查 | `hardFail` | 「X 笔通过 / Y 笔淘汰」 |
| ④ 排序比较 | 通过项排序 | `sortKey` | 排序依据摘要 |
| ⑤ 主推/备选 | 取前两名 | passed[0]/passed[1] | 主推卡 + 备选卡（或「无合格粮源」） |
| ⑥ 淘汰归因 | 每条淘汰原因 | 原因码模板 | 淘汰列表（原因码 + 一句解释） |
| ⑦ 待核验清单 | 交易前核验项 | 固定 5 条 + 缺失字段 | 核验项列表 |
| ⑧ 沉淀任务 | 保存任务 | 落库（用户触发） | 任务已保存 / 交接摘要 |

### 4.3 依赖拓扑与执行批次

依赖边：①→②→③；③→④；③→⑥；④→⑤；⑤→⑦；⑥→⑦；⑦→⑧。

④⑤ 链与 ⑥ 从 ③ 分叉后并行，在 ⑦ 汇合。前端按拓扑批次推进（每批约 500ms）：

| 批次 | 节点 |
|---|---|
| 1 | ① |
| 2 | ② |
| 3 | ③ |
| 4 | ④、⑥（并行） |
| 5 | ⑤ |
| 6 | ⑦ |
| 7 | ⑧（用户触发，非定时器） |

### 4.4 节点状态

`pending`（待执行）→ `running`（执行中，高亮闪烁）→ `done`（已完成，带产物徽标）；`skipped`（跳过，条件不足时不执行）。

---

## 5. 执行引擎（前端确定性）

- 自然语言 → `parseNeed`（已有，确定性正则）。
- DAG 节点逻辑 = `compareListings` 与 `parseNeed` 的分解，全部确定性纯函数。
- 前端定时器按第 4.3 节批次逐步推进节点状态，每批约 500ms；实际计算毫秒级完成，只是逐步揭示。
- 不接 LLM、不依赖模型、结果可复现。

### 5.1 空输入 / 无条件

- 自然语言未提取到任何条件（`parseNeed` 返回空）：① 产出「未识别到采购条件」，后续节点 `skipped`，提示补全需求。
- 部分条件（如只识别到品种）：照常跑，按已有条件过滤与排序。

## 6. 页面布局

```text
[我要找粮：描述寻源需求………………………]  [开始寻源]
────────────────────────────────────────────────────────
  DAG 画布：8 节点 + 有向边 + 状态高亮（running 节点闪烁）
────────────────────────────────────────────────────────
  节点产出面板：随执行逐步浮现中间产物
  （条件卡 → 通过/淘汰计数 → 主推/备选卡 → 淘汰列表 → 待核验）
────────────────────────────────────────────────────────
  最终结论区：主推/备选/淘汰/待核验
  [保存为任务] [交接运小二]
────────────────────────────────────────────────────────
  历史运行：已保存任务列表（点开回看快照）
```

- DAG 画布水平排布，节点为圆角块 + 图标，边为带箭头连线；分支与汇合处画分叉/汇合点。
- running 节点高亮 + 呼吸闪烁；done 节点换品牌色并显示「✓」。
- 窄屏（<lg）：画布横向可滚动，产出面板移到画布下方，历史运行列表正常堆叠。

## 7. 数据模型（单表 `sourcing_tasks`）

只保留任务收口所需，不拆条件为独立列（条件整体存 JSON）。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | int PK | 主键 |
| task_code | str(32) unique | 任务编号 `XZ20260823-001` |
| status | str(16) | `completed` / `handed_off` |
| need | JSON | 需求条件快照 |
| plan | JSON | 方案快照（主推/备选/淘汰/待核验） |
| handoff | JSON 可空 | 交接快照 |
| created_at / updated_at | datetime | 时间戳 |

### 7.1 `need` 快照

由 `parseNeed` 提取 + 条件换算得到，字段与候选对比的 `NeedInput` 一致；不包含目的地（目的地首版不在自然语言中提取，交接时补填）。

```json
{"variety":"玉米","quantity_tons":120,"grade":"二等","crop_year":2025,
 "deadline":"2026-08-30","budget_price":"2450"}
```

### 7.2 `plan` 快照（去规范化，冻结保存那一刻，不 join 粮源表）

```json
{
  "need_summary": {"variety":"玉米","quantity_tons":120,"grade":"二等","crop_year":2025,"deadline":"2026-08-30","budget_price":"2450"},
  "primary": {"listing_code":"LIANG-V1-001","variety_name":"玉米","grade":"二等","origin":"黑龙江绥化",
              "supplier_name":"北安粮贸","price":"2380","price_type":"出厂价",
              "available_quantity_tons":800,"latest_ship_at":"2026-08-28","reasons":[],"risks":[]},
  "backup": {…}|null,
  "eliminated": [{"listing_code":"LIANG-V1-003","variety_name":"玉米","grade":"三等",
                  "supplier_name":"铁岭粮贸","reason_code":"GRADE_BELOW_REQUIREMENT","reason_text":"…"}],
  "verifications": ["确认可锁定库存","获取正式质检单","确认报价有效期与含税口径","确认装运窗口","核验供应方主体与联系人"]
}
```

### 7.3 `handoff` 快照（结构化交接摘要，供下游小二消费）

```json
{"handoff_code":"YJ20260823-001","handed_off_at":"…",
 "summary":{"variety_name":"玉米","quantity_tons":120,"origin":"黑龙江绥化","destination":"深圳",
            "earliest_ship_at":"2026-08-25","latest_ship_at":"2026-08-28",
            "primary_listing_code":"LIANG-V1-001","supplier_name":"北安粮贸"}}
```

## 8. API 边界

- `POST /api/liang/tasks` → 保存任务（body：`need` + `plan`，`source` 默认 `workflow`；创建 `completed` 任务，后端生成 `task_code`）。
- `POST /api/liang/tasks/{id}/handoff` → 交接（body：`destination`，必填，前端交接弹窗补填；校验须有 plan；生成 handoff 快照，status→`handed_off`）。
- `GET /api/liang/tasks` → 历史运行列表（创建时间倒序）。
- `GET /api/liang/tasks/{id}` → 任务详情（回看快照）。

写操作均为页面显式按钮触发，交接为外向动作加前端确认（destination 为空时弹窗补填）。

---

## 9. 与「候选对比」的关系

- **候选对比**：轻量即时，面向「已有候选，快速并排对比」。
- **寻源任务**：正式编排执行，面向「自然语言需求，跑完整流程并沉淀交接」。

两者共用 `compareListings` 确定性结果，保证同一输入、同一主推/备选。首版不合并、不互相跳转（「开始寻源」在本 Tab 独立触发）。

---

## 10. 首版范围边界

**首版完成**：

- 8 节点 DAG 可视化画布 + 状态高亮 + 分支汇合。
- 自然语言输入 → 确定性提取 → 逐步执行。
- 节点产出面板随执行浮现中间产物。
- 最终结论区 + 保存任务 + 交接运小二。
- 单表 `sourcing_tasks` 落库 + 历史运行列表 + 详情回看。
- 固定、幂等、可复现的执行结果。

**首版不做**：

- 供应方 Tab（移除）。
- 历史记录 Tab（不在本文档范围）。
- 真 LLM / LangGraph 编排、SSE 流式进度。
- 真实对接运小二（只落结构化 mock 交接）。
- 编辑历史版本、多粮源拼单、自动联系/询价/下单。
- 公开数据接入、实时行情、刷新/同步。

## 11. 测试与验收

- 输入「120 吨二等玉米，7 天内可发」→ 8 节点按批次逐步点亮 → 主推北安、备选榆树、淘汰铁岭（等级不符）/通辽（数量不足），可复现。
- 节点进度可见、running 高亮、done 带徽标，中间产物随节点浮现。
- 保存任务后刷新仍在（后端落库）；交接生成结构化摘要、状态变已交接。
- 空输入 → ① 产出「未识别到采购条件」，后续节点 skipped。
- 无粮源通过硬条件 → ⑤ 产出「无合格粮源」，⑥ 逐条给淘汰原因。
- 页面不出现「演示数据 / mock」字样。
- 窄屏可完成输入、查看 DAG 进度、保存与交接。
