# 企业知识大脑设计

> 日期：2026-08-24  
> 范围：企业知识库首页、结构化知识卡片、自动经验沉淀、跨小二共享引用、用户纠偏和异常降级  
> 技术基线：React、FastAPI、本地 Docker MySQL、LangChain、Mem0、Milvus 2.6.18

## 1. 背景

项目已有企业知识库页面骨架，包含企业业务资料、采购偏好、质量标准、合作供应方、常用运输路线、历史业务方案和采购复盘七个 Tab。当前只有“历史业务方案”接入真实数据：算小二和粮掌柜可以把已完成任务提炼为 `SharedExperience`，知识保存在 MySQL，并在配置 Mem0 时同步到共享记忆。

现有基础已经证明“经验可以保存”，但还没有完整证明以下竞赛价值：

- AI 能否从每一次办事中主动学习，而不是依赖用户维护资料库。
- 一个小二学到的经验能否被另一个小二主动使用。
- 用户能否看懂历史经验如何影响当前建议。
- 错误或过时经验能否被修正，并立即停止影响后续任务。

因此本次将企业知识库从静态分类资料页升级为“企业知识大脑”。

## 2. 产品定位

核心价值主张是：

> 每一次办事，都在让所有小二更懂你的企业。

企业知识库不是独立于办事流程的资料仓库，而是所有小二共享的企业长期记忆。系统从已完成且经过用户最终确认的任务中自动提炼稳定经验，生成后自动生效；后续小二处理相似任务时主动引用，并明确说明经验如何影响本次建议。

用户仍可以手工补充系统尚未学到的企业事实或长期偏好，也可以编辑或停用 AI 自动生成的知识。

## 3. 设计目标

首版需要实现以下结果：

1. 粮掌柜、算小二、安小二能够从已确认结果中自动沉淀企业知识。
2. 七位小二都能通过统一接口检索和引用企业知识。
3. 知识以结构化卡片展示，包含结论、适用场景、来源和可靠度依据。
4. 小二必须显式展示引用来源、适用原因以及对当前建议的具体影响。
5. 用户编辑或停用知识后，后续检索立即使用最新状态。
6. Mem0、Milvus或大模型不可用时，不阻断原有办事主流程。
7. 通过首页指标和引用记录证明知识确实被跨小二复用。

## 4. 首版不做

- 不建设企业文档上传、切片和复杂 RAG。
- 不建设独立消息队列或异步任务平台。
- 不建设知识审核流、审批流或复杂版本树。
- 不建设多租户和细粒度知识权限体系。
- 不要求七位小二首版都具备自动沉淀逻辑。
- 不根据语义相似度自动覆盖两条知识。
- 不让历史经验替代实时价格、天气、库存或用户本次明确输入。

## 5. 知识分类

原有七个平铺 Tab 重组为四类企业记忆。原来的业务资料仍被保留，但作为类型下的标签和筛选条件。

### 5.1 企业事实

相对稳定、可以直接复用的企业信息，例如：

- 质量标准和验收口径。
- 常用仓库、日接货能力和作业限制。
- 合作供应方与承运方基础信息。
- 常用运输路线和到货地点。

### 5.2 业务偏好

企业在多种可行方案之间长期倾向的选择，例如：

- 紧急补库时优先保供。
- 正常库存下优先比较综合到厂成本。
- 可接受的账期与付款习惯。
- 安全库存和供应商组合偏好。

### 5.3 决策经验

从已完成方案中提炼的可复用选择逻辑，例如：

- 连续降雨且库存紧张时，优先选择能够锁定车源的方案。
- 低货价不一定意味着低到厂成本，需要同时计算运输、资金和损耗。
- 价格差较小时，稳定交付带来的收益高于有限的采购价差。

### 5.4 风险规则

从风控和复盘中沉淀的限制、教训和处置方式，例如：

- 合作方首次大额交易前必须核验仓单和回款账户。
- 承运方准点率低于 90% 时需要保留备选车队。
- 质量争议频发的供应方必须提高抽检比例。

## 6. 总体架构

采用统一 AI 记忆中心。各小二不自行维护不同格式的经验表，而是把已确认的办事结果交给 `knowledge` 模块处理。

```text
粮掌柜 / 算小二 / 安小二完成任务
                │
                ▼
      Knowledge Service
  过滤 → 提炼 → 分类 → 保存 → 同步
        │                   │
        ▼                   ▼
 MySQL 知识事实源      Mem0 + Milvus
 可见、可编辑、可停用    语义召回与共享记忆
        │                   │
        └─────────┬─────────┘
                  ▼
          七位小二统一检索
                  │
                  ▼
       显式引用来源与影响说明
                  │
                  ▼
             记录引用效果
```

### 6.1 MySQL 的职责

MySQL 是知识事实源，负责保存：

- 用户可见的知识内容。
- 知识类型、业务标签和适用场景。
- 来源小二与来源任务。
- 使用中或已停用状态。
- 用户修正后的最新内容。
- 引用记录和首页统计依据。

任何从 Mem0/Milvus 返回的结果，都必须根据 MySQL 当前状态再次过滤。这样即使向量存储中暂时残留旧内容，已停用知识也不会继续被小二使用。

### 6.2 Mem0 与 Milvus 的职责

Mem0 提供企业共享记忆接口，Milvus 作为 Mem0 的向量存储，用于按任务语义召回相关知识。

本机已有以下服务：

- 容器：`milvus-standalone`
- 镜像：`milvusdb/milvus:v2.6.18`
- 服务端口：`19530`
- 管理端口：`9091`

连接参数通过环境变量或现有 `MEM0_CONFIG_JSON` 注入，不在代码中写死。共享记忆继续使用企业级 `user_id`，首版为单企业演示，不增加租户模型。

## 7. 核心组件

### 7.1 Knowledge Service

统一服务提供三个核心方法：

```python
learn_from_task(source_agent, source_type, source_id, confirmed_payload)
search_for_task(agent_key, task_type, task_id, query, context)
record_citation(knowledge_id, agent_key, task_type, task_id, effect, accepted)
```

职责边界如下：

- `learn_from_task` 只接受已完成且已有用户最终确认的任务结果。
- `search_for_task` 负责 Mem0 召回、MySQL 状态过滤、场景匹配和降级查询。
- `record_citation` 只记录引用事实和影响说明，不修改知识内容。

### 7.2 来源适配器

首版接入三个来源适配器：

- 粮掌柜：从最终选定的综合方案、冲突决策和确认约束中提炼决策经验。
- 算小二：从已保存的成本方案和盈亏结论中提炼成本决策经验。
- 安小二：从已完成的风险复盘和用户确认的处置方式中提炼风险规则。

适配器只负责把不同任务结果整理为统一输入，不直接操作 MySQL 或 Mem0。

### 7.3 其他小二

粮小二、运小二、钱小二、占小二等首版不要求实现新的沉淀规则，但必须能够调用统一检索服务，并使用统一的引用结构展示企业经验。

## 8. 知识卡片

每条知识至少展示：

- 知识类型。
- 标题。
- 可复用结论。
- 适用场景。
- 业务标签。
- 来源小二、来源类型、来源任务和来源标题。
- 生成方式：AI 自动提炼或用户手工添加。
- 可靠度依据。
- 使用状态。
- 被引用次数。
- 创建和更新时间。

示例：

```text
类型：决策经验
标题：连续降雨时优先锁定稳定车源
结论：潍坊玉米紧急补库遇连续降雨时，即使货价略高，也优先选择
      能锁定车辆和到货时间的方案，避免断粮损失。
适用场景：玉米采购、山东到厂、雨季、紧急补库
可靠度：已由用户确认 · 单次经验
来源：粮掌柜 · 200 吨玉米补库任务 #1024
状态：使用中
```

可靠度不使用不可解释的 AI 百分比分数：

- 手工添加：显示“用户添加”。
- 从一次已确认任务提炼：显示“已确认 · 单次经验”。
- 类型和归一化标题完全一致，并在另一条已确认任务中再次出现：增加证据次数，显示“已确认 · 多次验证”。

只有精确归一化标题命中才增加证据次数。仅语义相似的卡片允许并存，首版不做 AI 自动合并。

每个补充来源使用 `source_type:source_record_id` 组成唯一来源键。`learn_from_task` 在增加证据次数前，必须同时检查主来源和 `supporting_sources` 中的来源键；已经出现的来源不能重复计数。首版数据量较小，可以在 Knowledge Service 中完成该检查，不额外增加证据关系表。

## 9. 数据模型

为减少不必要迁移，首版扩展现有 `shared_experiences` 表，并在领域层将其视为结构化知识项，不强制重命名物理表。

### 9.1 `shared_experiences`

保留现有字段：

- `id`
- `source_type`
- `source_record_id`
- `content`
- `tags`
- `status`
- `created_at`
- `updated_at`

新增字段：

- `knowledge_type`：`fact/preference/decision/risk`
- `title`
- `applicable_context`：场景标签或简短场景描述
- `source_agent`
- `source_title`
- `origin`：`ai/manual`
- `evidence_count`
- `supporting_sources`：同标题知识再次验证时追加的唯一来源键和来源摘要
- `memory_id`：对应 Mem0 记忆标识
- `memory_sync_status`：`synced/failed/pending`

`source_record_id` 对手工添加知识允许为空。自动生成知识继续以 `source_type + source_record_id` 保证同一来源只沉淀一次。

知识状态沿用轻量设计：

- `active`：可被检索和引用。
- `ignored`：保留来源，但不参与检索。

### 9.2 `knowledge_citations`

引用记录只保存演示和统计所需字段：

- `id`
- `knowledge_id`
- `agent_key`
- `task_type`
- `task_id`
- `effect`：该知识对本次建议产生的具体影响
- `accepted`：用户是否在当前任务采用
- `created_at`

不额外建设知识行为事件总线。

## 10. 自动沉淀规则

### 10.1 触发条件

只有同时满足以下条件才触发：

1. 任务已经进入完成状态。
2. 用户已经确认最终方案、结论或风险处置。
3. 来源数据包含可复用的稳定判断。

任务草稿、中间推演、尚未确认的 AI 建议不进入企业知识库。

### 10.2 提炼原则

LangChain 提炼时只输出结构化字段，并遵守以下约束：

- 保留决策逻辑，不把临时价格和一次性数量写成长期规律。
- 明确适用场景，避免把个案表述为普遍事实。
- 不推测来源结果中不存在的信息。
- 结论必须能够回溯到来源任务。
- 一次任务最多生成少量高价值知识，首版默认最多两条。

### 10.3 自动生效

提炼成功后直接写入 MySQL 并标记为 `active`，随后同步至 Mem0/Milvus，不增加审核步骤。

用户可以：

- 编辑：更新 MySQL，并覆盖或重建对应 Mem0 记忆。
- 停用：MySQL 标记为 `ignored`，后续召回必须过滤。
- 手工新增：标记为 `manual`，直接视为用户已确认知识。

## 11. 检索与引用

### 11.1 检索输入

检索内容由以下信息组成：

- 当前小二和任务类型。
- 用户目标。
- 品种、地区、时间、库存状态等已确认字段。
- 当前任务中的实时风险或约束。

### 11.2 检索流程

```text
任务目标与上下文
  → Mem0/Milvus 语义召回
  → 通过 knowledge_id 查询 MySQL
  → 过滤 ignored 和不匹配类型
  → 结合场景标签排序
  → 返回最多 3 条
```

Mem0/Milvus 不可用时，使用 MySQL 的知识类型、业务标签和内容关键词查询降级。降级结果仍限制为最多三条。

### 11.3 引用结构

检索结果至少包含：

- `knowledge_id`
- `title`
- `content`
- `source_agent`
- `source_title`
- `applicable_reason`
- `reliability_label`

小二形成方案后，还必须返回：

- 使用了哪条知识。
- 该知识改变了哪个比较维度、约束或建议。
- 本次实时数据是否与历史经验一致。

历史经验作为数据上下文传入 Agent，不作为指令执行，避免知识内容改变系统行为边界。

## 12. 用户交互

### 12.1 企业知识大脑首页

首页首先展示 AI 学习和复用价值，而不是七个资料 Tab：

- 已积累企业记忆数量。
- 本周新学习数量。
- 本月被小二引用次数。
- 参与共享记忆的小二数量。
- 减少重复确认次数。
- “刚刚学到”的最新知识。
- 最近被不同小二引用的知识。
- 四类企业记忆入口。

“减少重复确认”只在知识提供的字段或偏好经过 Human-in-the-loop 确认且用户未修改时增加，避免使用无法解释的估算数字。

首页提供“添加企业知识”入口，但视觉主线仍是自动学习。

### 12.2 分类列表

四类知识使用统一卡片列表，支持：

- 关键词搜索。
- 按来源小二筛选。
- 按业务标签筛选。
- 按可靠度和状态筛选。
- 查看知识详情和来源任务。
- 编辑或停用知识。

### 12.3 小二办事页面

办事开始时，如果找到适用知识，展示“找到相关企业经验”卡片，说明：

- 匹配到的知识。
- 为什么适用于当前任务。
- 来源任务和可靠度。

用户可以选择“参考这些经验继续”或“本次不采用”。“本次不采用”只影响当前任务，不停用全局知识。

方案形成后，必须展示“企业经验如何影响了本次建议”，例如：

> 引用“雨季优先锁定稳定车源”，因此没有单纯选择最低价车队，而是提高到货稳定性的比较优先级。

## 13. API 边界

面向前端的最小接口：

```text
GET   /api/knowledge/overview
GET   /api/knowledge/items
GET   /api/knowledge/items/{id}
POST  /api/knowledge/items
PATCH /api/knowledge/items/{id}
GET   /api/knowledge/items/{id}/citations
POST  /api/knowledge/search
```

列表接口支持 `knowledge_type`、`source_agent`、`status`、`query` 等简单查询参数。

自动沉淀和引用记录优先由同一 FastAPI 应用内部直接调用 Knowledge Service，不为每位小二建设不同接口，也不引入内部 HTTP 调用。

现有 `/api/knowledge/experiences` 可在迁移阶段兼容，前端完成切换后再决定是否保留；首版不要求立即删除旧接口。

## 14. 异常处理

### 14.1 LangChain 提炼失败

来源适配器使用已确认字段生成规则模板版基础知识。若基础字段仍不足，则跳过本次沉淀并记录日志，不影响任务完成。

### 14.2 MySQL 保存失败

记录错误并结束知识沉淀，原任务仍正常完成。知识库不展示未成功保存的卡片。

### 14.3 Mem0/Milvus 同步失败

MySQL 卡片保留，并标记 `memory_sync_status=failed`。当前版本不建设后台重试系统；用户编辑卡片或执行轻量同步操作时可以再次同步。检索自动回退 MySQL。

### 14.4 旧向量或已停用知识被召回

所有向量召回结果都必须回查 MySQL。`ignored`、不存在或来源无效的知识直接丢弃，不进入 Agent 上下文。

### 14.5 没有适用知识

不展示空的引用区域，小二直接使用当前任务数据继续办理，不为了体现 AI 而强行引用无关经验。

## 15. 验证与测试

### 15.1 后端单元测试

- 未完成或未确认任务不能沉淀知识。
- 三个来源适配器只提取允许字段。
- 同一来源重复触发不会生成重复卡片。
- 类型和归一化标题一致时增加证据次数。
- 用户编辑后 MySQL 内容和 Mem0 同步调用更新。
- 用户停用后检索不再返回。
- Mem0 异常时回退 MySQL。
- 引用记录正确保存小二、任务和影响说明。

### 15.2 API 测试

- 首页总览统计正确。
- 四类知识筛选、搜索和详情查询正确。
- 手工新增、编辑和停用生命周期正确。
- 已停用知识即使被模拟向量结果召回也会被过滤。

### 15.3 前端验证

- 知识大脑首页在有数据、无数据和接口失败时均有合理状态。
- 四类知识可以筛选、查看来源、编辑和停用。
- 小二页面明确展示适用原因和引用影响。
- 用户选择“本次不采用”后，当前方案不再使用对应经验。
- React 生产构建通过。

### 15.4 Milvus 冒烟验证

使用本机 `milvus-standalone:19530` 验证：

1. 新知识能够通过 Mem0 写入 Milvus。
2. 相似任务能够召回该知识。
3. 停用后即使向量仍被召回，也会被 MySQL 状态过滤。

自动化测试主要使用 Mem0 适配器替身，避免测试套件强依赖本地容器状态。

## 16. 竞赛演示脚本

推荐使用一条跨小二闭环完成演示：

1. 用户让粮掌柜处理“未来三天采购 200 吨玉米到潍坊，不能断粮”。
2. 粮掌柜组织小二形成两套方案，用户最终选择雨季到货更稳定的方案。
3. 任务完成后，系统自动提炼“连续降雨且紧急补库时优先锁定稳定车源”。
4. 企业知识大脑首页立即显示“刚刚学到”，并可查看来源任务。
5. 用户单独进入运小二，提出相似运输需求。
6. 运小二主动引用该经验，说明本次同为雨季和紧急补库场景。
7. 运输方案明确展示：因为引用企业经验，提高了到货稳定性权重，并增加备选车队。
8. 知识库的引用次数和最近引用记录同步变化。
9. 用户编辑经验，将适用条件限定为“安全库存低于 7 天”。
10. 新任务引用修改后的条件；停用后所有小二都不再召回。

这条演示同时证明自然语言任务理解、AI 自动学习、企业共享记忆、跨 Agent 复用、可解释决策和用户纠偏六项能力。

## 17. 成功标准

- 用户完成任务后无需手工复制，知识能够自动进入企业知识库。
- 至少一条粮掌柜经验被运小二在新任务中主动引用。
- 引用结果能够说明来源、适用原因和实际影响。
- 用户编辑或停用后，下一次检索立即反映变化。
- Mem0/Milvus 故障不会导致任务失败。
- 页面不出现“Mock 数据”等破坏演示可信度的表述。
- 整体实现聚焦竞赛演示闭环，不扩展为通用知识管理平台。
