# 粮掌柜｜复杂采购多 Agent 协作指挥舱设计规格

> 文档日期：2026-08-24  
> 文档状态：设计已确认  
> 设计范围：粮掌柜独立服务页、复杂采购任务编排、多 Agent 协作、Human-in-the-loop、2.5D 指挥舱、行动任务与企业经验沉淀  
> 主演示场景：饲料厂未来 15 天采购 200 吨二等玉米

## 1. 设计结论

粮掌柜不是第七个专业小二，也不是普通聊天助手，而是面向复杂粮食采购目标的 AI 任务主理人：理解目标、按需组建小二团队、并行推进专业分析、识别跨专业冲突，并在用户确认后生成可执行任务。

本设计采用以下已确认方向：

- 产品主线：复杂采购不会统筹。
- 办事终点：形成决策方案，并生成可由专业小二继续办理的行动任务。
- 冲突处理：展示分歧并给出有条件推荐，最终由用户确认。
- 主演示案例：15 天内完成 200 吨玉米补库。
- 协作架构：粮掌柜中央编排，专业小二并行办理。
- 人机关系：关键节点嵌入 Human-in-the-loop，AI 不自动越权。
- 页面形态：单页 2.5D 多 Agent 协作指挥舱。
- 技术边界：CSS 2.5D、SVG 动态连线、React 状态驱动，不使用 Three.js 或 WebGL。

## 2. 用户痛点与产品目标

### 2.1 真实痛点

粮达网 Plus 的六位专业小二已经覆盖行情、粮源、物流、综合成本、资金和风险，但复杂采购仍存在四类断点：

1. 用户知道采购目标，却不知道先找谁、需要哪些专业角色参与。
2. 专业结论散落在多个页面和任务中，用户需要人工整理并建立关联。
3. 成本、时效、行情和风险可能互相冲突，简单拼接报告无法帮助用户做取舍。
4. AI 分析结束后缺少明确行动，用户仍需重新组织询价、询运和核验等事项。

### 2.2 产品目标

用户只需要描述业务目标，粮掌柜就能：

- 提取并补齐关键采购条件。
- 说明需要哪些小二参与以及为什么。
- 让专业小二并行形成独立、可追溯的结果。
- 识别影响采购决策的专业冲突。
- 给出主推、备选、淘汰原因和切换条件。
- 在用户确认后生成后续行动任务。
- 将稳定、已确认的经验沉淀为企业共享记忆。

### 2.3 非目标

首版不建设新的粮食交易系统，不负责真实下单、签约、付款或放款。粮掌柜不替代专业小二，也不把六位小二串成固定流水线。

## 3. 角色边界

### 3.1 粮掌柜负责

- 理解复杂业务目标。
- 检索企业共享记忆并标明来源。
- 识别关键缺失条件。
- 推荐参与小二及任务边界。
- 生成结构化子任务并组织并行办理。
- 统一接收各小二结果。
- 检测信息缺口和跨专业冲突。
- 形成条件化综合建议。
- 设置人工决策闸门。
- 根据用户确认生成行动任务。

### 3.2 粮掌柜不负责

- 替瞻小二独立生成行情判断。
- 替粮小二搜索和选择具体粮源。
- 替运小二规划物流服务。
- 替算小二重新计算综合成本。
- 替钱小二承诺授信、审批或放款结果。
- 替安小二降低风险等级。
- 未经确认改变质量、预算、交期或风险底线。

### 3.3 专业小二负责

- 在自己的专业边界内完成分析。
- 返回统一外层结构的专业结果。
- 保留自己的原始结论和依据。
- 响应粮掌柜最多一次定向补充请求。
- 在用户确认后承接后续行动任务。

## 4. 主演示场景

用户是一家饲料企业的采购人员，需要在未来 15 天内采购 200 吨二等玉米并按时到厂。用户优先保证生产连续性，同时希望控制综合吨成本。

粮掌柜从一句自然语言目标开始，结合企业过往采购偏好，推荐瞻、粮、运、算、安五位小二参与。由于当前不存在资金缺口，钱小二保持待命并说明未参与原因。

各小二并行办理后形成两套可比较的完整采购组合：

- 方案 A 综合成本最低，但供应方近半年履约证据不足。
- 方案 B 每吨贵 18 元，但交付稳定性更高。

粮掌柜不抹平分歧，给出条件化建议：

> A 补齐履约担保后优先；如果今日无法完成核验或核验不通过，立即切换 B，避免影响 15 天保供目标。

用户确认先核验 A 后，系统生成安小二风险核验任务；核验通过后才允许创建粮小二询价任务和运小二运输对接任务。

## 5. 核心办事流程

### 5.1 用户描述目标

用户可以直接输入：

> 未来 15 天帮我采购 200 吨玉米，别影响生产，综合成本尽量控制在 2500 元/吨以内。

页面允许用户粘贴报价、采购计划或已有业务资料，但首版不要求先填写完整表单。

### 5.2 AI 整理目标

粮掌柜提取：

- 品种和等级。
- 数量。
- 到货地点。
- 到货窗口。
- 质量底线。
- 预算或目标成本。
- 库存和保供约束。
- 是否存在资金缺口。

粮掌柜可以引用企业共享记忆补充偏好，但必须标记为“企业过往经验”，不能当成本次已确认事实。

### 5.3 目标确认闸门

用户确认会影响结果的关键条件。非关键缺失项可以标为暂估，不进行无休止追问。关键条件未确认前不启动专业小二。

### 5.4 AI 按需组队

粮掌柜展示建议参与的小二、邀请原因、预期产出和任务边界。用户确认团队后才启动协作。

### 5.5 专业小二并行办理

各小二接收结构化子任务并独立运行。前端持续显示状态、结果回传和必要的跨小二交接。

### 5.6 冲突识别与定向补充

粮掌柜通过确定性规则识别影响业务决策的冲突。存在冲突时，只向直接相关的小二发起一次补充请求，不组织无限自由讨论。

### 5.7 综合方案与条件化推荐

粮掌柜输出：

- 主推方案。
- 备选方案。
- 淘汰方案及原因。
- 各专业意见和依据。
- 方案取舍。
- 推荐生效条件。
- 条件不满足时的切换方案。
- 需要用户处理的确认项。

### 5.8 决策与执行闸门

用户选择方案并确认下一步动作。确认后才创建询价、询运、风险核验或资金服务等行动任务。

### 5.9 经验沉淀

任务完成后，系统只提炼稳定且经过用户确认的企业经验。用户可以编辑或忽略经验，不建设独立审核流程。

## 6. Human-in-the-loop 设计

### 6.1 三类人工闸门

1. **目标口径确认**：确认品种、数量、质量底线、交期、到货地和预算等关键条件。
2. **协作范围确认**：确认邀请哪些小二、各自负责什么，以及是否扩大任务范围。
3. **方案与执行确认**：选择主推或备选方案，确认是否创建后续行动任务。

处理中如果需要新增小二、放宽业务底线或产生高影响动作，应回到对应类型的人工闸门。

### 6.2 无需确认的动作

- 页面筛选和视图切换。
- 读取任务状态。
- 汇总只读结果。
- 展示判断依据和数据来源。
- 在既定范围内执行一次定向补充分析。

### 6.3 决策闸门内容

每个闸门必须说明：

- 为什么需要用户确认。
- 粮掌柜的建议及依据。
- 用户有哪些可选动作。
- 每个选择会触发什么。
- 不确认或选择备选的业务影响。

高影响动作默认不预选。用户确认后写入决策轨迹。

### 6.4 暂停与恢复

等待用户确认时，LangGraph 暂停并将当前任务快照保存到 MySQL。用户确认后从对应节点恢复，不重新执行整个任务。

## 7. 页面信息架构

粮掌柜服务页只保留两个轻量入口：

- 开始新任务。
- 历史任务。

进入具体任务后，不再使用“目标受理、任务方案、参与小二、综合结论、行动清单”等六个平级 Tab，而是使用单页任务指挥舱。

### 7.1 新任务首页

首屏包含：

- 自然语言目标输入框。
- 粘贴或上传业务资料入口。
- 玉米补库等真实任务示例。
- 企业历史偏好提示。
- 最近未完成任务入口。

### 7.2 指挥舱顶部任务条

显示：

- 任务名称和业务目标。
- 整体进度。
- 参与小二数量。
- 当前阶段。
- 待用户确认数量。

### 7.3 左侧任务推进轨

阶段固定为：

1. 目标确认。
2. 智能组队。
3. 并行办理。
4. 冲突会商。
5. 方案确认。
6. 执行分派。

推进轨只用于定位进度，不要求用户逐页操作。

### 7.4 中央 2.5D 协作沙盘

粮掌柜位于中央。空间深度承担业务语义：

- 后景：已完成或待命的小二。
- 中景：正在并行办理的小二。
- 前景：与当前冲突或决策直接相关的小二。
- 最前层：当前 Human-in-the-loop 决策闸门。

连线语义：

- 蓝色动态连线：正常结构化结果交接。
- 橙色动态连线：风险异议或专业冲突。
- 灰色弱化连线：待命或未参与。

点击小二后展开其任务、结论、依据、来源和待确认项。沙盘动画必须由真实任务状态驱动，不能只是循环播放的装饰动画。

### 7.5 右侧决策面板

始终只展示当前最需要用户处理的事项：

- 补充关键条件。
- 确认协作团队。
- 处理专业冲突。
- 选择采购方案。
- 创建行动任务。

没有人工待办时，显示粮掌柜当前判断和下一步预计动作。

### 7.6 专业结果抽屉

专业结果包含：

- 小二接收的任务。
- 已确认输入和暂估输入。
- 核心结论。
- 判断依据。
- 数据来源与更新时间。
- 风险、异议和缺失信息。
- 对综合方案的影响。

需要深入操作时，再跳转到对应小二独立服务页并携带当前任务上下文。

### 7.7 综合方案对比

专业结果基本齐备后，中央区域展示主推、备选和淘汰方案，至少包含：

- 综合吨成本。
- 到货时间。
- 关键质量指标。
- 主要风险。
- 专业小二意见。
- 生效条件和切换条件。

首版不使用不透明的 AI 综合评分。

### 7.8 响应式边界

竞赛演示优先适配桌面宽屏。窄屏下降级为纵向任务流和小二状态卡，不强行保留 2.5D 空间。

## 8. 2.5D 技术实现边界

视觉层使用：

- CSS `perspective`、`translate3d`、缩放、透明度和模糊表现纵深。
- SVG 路径和虚线动画表现 Agent 数据流。
- CSS 渐变和轨道动画表现中央全息核心。
- React 状态控制 Agent 位置、层级、亮度、状态和连线。

首版不使用 Three.js、WebGL、三维模型、自由摄像机和复杂遮挡计算。

动画只改变 `transform` 和 `opacity` 等低开销属性。页面不可见时暂停非必要动画，窄屏和低性能设备降级为静态状态卡。

## 9. 多 Agent 编排架构

### 9.1 架构选择

采用“粮掌柜中央编排 + 专业小二并行办理”：

- LangGraph 负责状态推进、并行节点、暂停和恢复。
- LangChain 承载粮掌柜和各专业小二的模型能力。
- 确定性规则负责组队兜底、成本口径、冲突识别和高风险动作限制。
- MySQL 保存任务、运行结果和人工决策。
- mem0 提供企业共享记忆，失败时回退 MySQL 查询。

不采用单一超级 Agent 模拟全部角色，也不采用六位小二无限自由讨论。

### 9.2 编排主图

```text
接收目标
  ↓
检索企业共享记忆
  ↓
提取并补齐关键条件
  ↓
【人工确认目标】
  ↓
推荐参与小二及分工
  ↓
【人工确认协作团队】
  ↓
并行调用专业小二
  ↓
统一结构化结果
  ↓
检测信息缺口与专业冲突
  ├─ 无冲突 → 形成综合方案
  └─ 有冲突 → 定向补充一次 → 形成条件化推荐
                                      ↓
                                【人工确认方案】
                                      ↓
                                  创建行动任务
                                      ↓
                                  沉淀业务经验
```

### 9.3 专业结果统一协议

每位小二返回统一外层结构：

```json
{
  "agent_id": "an",
  "status": "completed_with_objection",
  "summary": "A 供应方履约证据不足",
  "facts": [],
  "recommendations": [],
  "risks": [],
  "missing_information": [],
  "evidence": [],
  "impact_on_mission": "需要在选择 A 前完成履约担保核验",
  "available_actions": []
}
```

不同小二可以在 `facts` 和 `available_actions` 中保留专业字段，但粮掌柜只依赖统一外层协议。

### 9.4 动态组队规则

- 涉及采购时机：邀请瞻小二。
- 需要寻找供应来源：邀请粮小二。
- 涉及到厂、运输或分批交付：邀请运小二。
- 存在多套组合或综合成本判断：邀请算小二。
- 涉及合作方、履约、质量或合同风险：邀请安小二。
- 存在资金缺口或账期需求：邀请钱小二。

LLM 理解用户表达并解释邀请原因，确定性规则负责最终能力匹配和兜底。用户可以增减小二，系统必须说明可能失去的分析内容。

### 9.5 并行办理

用户确认团队后，互不依赖的小二并行运行。存在明确依赖时才顺序执行，例如算小二需要消费粮源、运输和资金成本结果。

并行不是让所有小二同时输出对话，而是让多个专业节点同时处理独立子任务，并持续写入结构化状态。

### 9.6 冲突识别

首版处理五类冲突：

- 成本更低，但风险更高。
- 价格更低，但交期不满足。
- 行情建议等待，但库存只能支撑较短时间。
- 资金成本可接受，但审批周期超过采购窗口。
- 粮源质量更优，但到厂综合成本明显偏高。

确定性规则识别冲突，LLM 负责生成易理解的取舍说明。每个冲突最多触发一次定向补充，补充后必须进入建议或人工确认，不继续循环。

### 9.7 条件化推荐协议

每条综合推荐必须包含：

- 推荐方案。
- 推荐依据。
- 需要牺牲的事项。
- 推荐生效前提。
- 前提不满足时的切换方案。
- 下一步承接小二。
- 需要用户确认的动作。

## 10. 企业共享记忆

### 10.1 可沉淀内容

- 企业通常优先保供，再比较成本。
- 明确、稳定的质量底线。
- 工厂单日最大接卸能力。
- 常用到货节奏和分批偏好。
- 用户确认过的风险处置经验。

### 10.2 不沉淀内容

- 未经用户确认的模型推断。
- 单次临时报价。
- 本次任务的暂估字段。
- 已失效的市场判断。
- 小二之间尚未解决的分歧。

### 10.3 引用规则

记忆必须显示来源和适用场景，并允许用户编辑或忽略。历史经验不能覆盖本次实时数据，也不能替代用户明确输入。

## 11. 系统组件

### 11.1 前端组件

- `MissionStart`：自然语言目标输入和最近任务。
- `GoalConfirmation`：目标字段确认。
- `TeamConfirmation`：小二团队与职责确认。
- `MissionCockpit`：指挥舱外壳。
- `SpatialAgentStage`：2.5D 协作沙盘。
- `AgentPod`：单个小二空间节点。
- `AgentFlowLink`：结果交接和冲突连线。
- `MissionRail`：任务阶段。
- `DecisionGate`：人工决策闸门。
- `AgentResultDrawer`：专业结果详情。
- `PlanComparison`：方案对比。
- `DecisionTrace`：AI 与用户决策轨迹。
- `ActionTaskList`：后续行动任务。

空间舞台只负责状态表现，业务详情、确认逻辑和数据请求由独立组件承担。

## 12. 最小数据模型

### 12.1 采购任务 `procurement_missions`

- 任务编号和名称。
- 用户原始描述。
- 结构化采购目标。
- 当前阶段和状态。
- 综合方案结果。
- 创建和更新时间。

### 12.2 小二办理记录 `mission_agent_runs`

- 所属任务。
- 小二标识。
- 参与原因。
- 子任务输入。
- 当前状态。
- 结构化输出。
- 异常信息。

### 12.3 人工决策记录 `mission_decisions`

- 所属任务。
- 闸门类型。
- AI 建议和可选动作。
- 用户选择和补充说明。
- 确认时间。

### 12.4 行动任务 `mission_action_tasks`

- 来源采购任务。
- 承接小二。
- 结构化任务内容。
- 当前状态。
- 前置行动任务。
- 与原方案的关联。

行动任务允许使用“等待前置任务”状态。例如用户选择先核验 A 时，安小二核验任务立即进入待办理，询价和运输对接任务同时生成但保持等待；只有核验通过后才允许继续。

首版不建设软删除、复杂版本树、独立事件表、消息队列或分布式调度。

## 13. 状态与数据流

### 13.1 任务状态

- `awaiting_goal_confirmation`：目标待确认。
- `awaiting_team_confirmation`：团队待确认。
- `running`：办理中。
- `awaiting_decision`：决策待确认。
- `partially_completed`：部分完成。
- `completed`：已完成。
- `failed`：无法形成可用方案。

单个小二失败不会直接让整个任务失败。

### 13.2 页面数据流

```text
用户输入目标
  → 粮掌柜提取目标并查询企业经验
  → 用户确认目标
  → 粮掌柜生成组队方案
  → 用户确认团队
  → 后端并行调用专业小二
  → 状态和结果写入 MySQL
  → 前端持续更新 2.5D 沙盘
  → 冲突规则生成冲突事件
  → 粮掌柜形成条件化推荐
  → 用户通过决策闸门确认
  → 创建行动任务并沉淀经验
```

运行进度使用 HTTP NDJSON 流返回，不建设 SSE、WebSocket 或独立事件平台。页面刷新后从 MySQL 恢复完整任务快照。

## 14. API 设计

- `POST /api/zhanggui/missions/preview`：解析自然语言目标并返回待确认字段。
- `POST /api/zhanggui/missions`：根据原始描述和预览结果创建目标待确认的采购任务。
- `GET /api/zhanggui/missions`：获取历史任务。
- `GET /api/zhanggui/missions/{mission_id}`：获取任务完整快照。
- `POST /api/zhanggui/missions/{mission_id}/confirm-goal`：确认目标并生成组队建议。
- `POST /api/zhanggui/missions/{mission_id}/confirm-team`：确认团队并准备运行。
- `POST /api/zhanggui/missions/{mission_id}/run`：运行或恢复任务，直到下一人工闸门。
- `POST /api/zhanggui/missions/{mission_id}/decisions/{decision_id}`：提交人工决策。
- `GET /api/zhanggui/missions/{mission_id}/events`：以 NDJSON 流返回任务运行进度。

所有高影响写操作必须校验任务当前状态，避免重复确认或越过人工闸门。

## 15. 异常与降级

### 15.1 单个小二失败

其他小二继续运行。粮掌柜标记结果不完整，并说明缺失结果可能影响哪些结论。用户可以重试、跳过或使用暂估值。

### 15.2 大模型不可用

保留规则组队、结构化数据、确定性冲突检测和固定解释模板。页面显示能力已降级，不伪装成完整 AI 分析。

### 15.3 关键字段缺失

任务停在目标确认闸门，不生成虚假精确结论。

### 15.4 专业结果超时

用户可以继续等待、重试该小二或在明确提示下跳过。超时结果不得静默进入综合方案。

### 15.5 共享记忆不可用

回退 MySQL 企业经验查询；仍不可用时不引用历史经验，不影响主流程。

### 15.6 页面刷新或连接中断

前端重新获取任务快照并恢复当前阶段、Agent 状态、决策闸门和已完成结果。

## 16. 首版数据范围

- 3 个候选粮源。
- 2 套运输方案。

- 1 个主推方案和 1 个备选方案。

## 17. 测试设计

### 17.1 规则单元测试

- 不同采购目标推荐正确的小二组合。
- 无资金缺口时不邀请钱小二。
- 五类冲突能够被稳定识别。
- 每个冲突最多触发一次补充。
- 高影响动作无法越过人工闸门。

### 17.2 LangGraph 流程测试

- 目标确认前不运行专业小二。
- 团队确认后可并行运行独立节点。
- 存在依赖的算小二在前置结果齐备后运行。
- 图能够在三个确认闸门暂停和恢复。
- 单小二失败时任务进入可解释的部分完成状态。
- 完成后正确生成行动任务和企业经验候选。

### 17.3 API 测试

- 创建、读取和恢复任务。
- 重复确认被拒绝。
- 状态不匹配的运行请求被拒绝。
- 进度事件与任务快照一致。
- 页面刷新后返回相同的决策轨迹。

### 17.4 前端测试

- Agent 空间层级和连线随状态变化。
- 未参与小二明确显示原因。
- 点击小二可以查看专业结果。
- 冲突出现时橙色连线和决策面板同步出现。
- 未确认前不能创建行动任务。
- 窄屏正确降级为纵向列表。

## 18. 首版验收标准

核心演示必须完整跑通：

1. 用户输入一句自然语言采购目标。
2. AI 提取条件并引用一条有来源的企业历史偏好。
3. 用户确认目标。
4. 粮掌柜推荐五位小二，并说明钱小二不参与的原因。
5. 用户确认团队。
6. 多位小二在指挥舱中显示真实并行办理状态。
7. 算小二和安小二形成可见冲突。
8. 粮掌柜给出带生效条件和切换条件的推荐。
9. 用户通过 Human-in-the-loop 闸门选择方案。
10. 系统生成风险核验、询价和运输任务。
11. 刷新页面后仍能恢复任务和决策轨迹。
12. 完成记录生成一条可被其他小二引用的企业经验。

## 19. 首版明确不做

- 真实交易、合同、付款或资金申请。
- 六位小二无限自由会商。
- 自动替用户放宽业务底线。
- 自动执行高影响动作。
- Three.js、WebGL 和可自由旋转的真 3D。
- 通用多 Agent 开发平台。
- 复杂权限、软删除、消息队列和分布式任务调度。
- 覆盖所有粮食品种和全部异常场景。

## 20. 竞赛演示脚本

1. 用户从首页点击中央粮掌柜。
2. 输入“未来 15 天采购 200 吨二等玉米，不能影响生产”。
3. 粮掌柜引用企业“优先保供、再比较成本”的历史经验，并要求用户确认质量和到货条件。
4. 用户确认目标后，粮掌柜推荐瞻、粮、运、算、安五位小二，钱小二保持待命。
5. 用户确认团队，2.5D 沙盘显示多个专业节点并行运行和结果回传。
6. 算小二支持成本最低的 A，安小二提出履约证据不足的异议，蓝色数据流切换为橙色冲突连线。
7. 粮掌柜给出“A 补齐履约担保后优先，否则切换 B”的条件化建议。
8. 用户确认先核验 A，系统生成安小二核验任务，并锁住未经核验的询价和运输动作。
9. 用户进入行动清单，查看风险核验、询价和运输对接任务。
10. 返回历史任务，展示完整决策轨迹和自动沉淀的企业经验。

该脚本同时证明自然语言目标理解、真实多 Agent 编排、专业冲突处理、Human-in-the-loop、可执行任务闭环和共享记忆六项核心能力。
