# 粮小二第二 Tab「候选对比」设计规格

> 日期：2026-08-23
> 状态：已确认
> 范围：粮小二「候选对比」Tab 的对比与主推/备选输出。承接第一 Tab 的候选篮与「我要找粮」需求。不涉及供应方、寻源任务、历史记录。

---

## 1. 设计目标

候选对比是「比和定」：把候选粮源对比，在用户有明确需求条件时输出**主推、备选、淘汰原因、待核验清单**；没有条件时只做并排对比，不强推。

真实痛点：

- 采购员面对多笔粮源，缺一个「逐字段并排对比」的视角，容易遗漏价格口径、发运时间、质检差异。
- 最低价不一定满足质量、数量、发运，人工容易漏掉硬条件。
- 决策需要「主推谁、备选谁、为什么淘汰、下单前核验什么」，而不是一段泛泛建议。

成功标准：

- 同样输入（候选 + 条件）得到稳定可复现的主推、备选、淘汰原因。
- 不满足硬条件的粮源绝不成为主推，即使价格更低。
- 无需求条件时不伪造主推/备选。
- 全程确定性计算，不接 LLM、不落库。

---

## 2. 已确认的核心决策

1. **对比范围**：候选篮优先；候选篮为空时，用需求条件从全部粮源硬过滤。
2. **主推前提**：有明确需求条件才出主推/备选；无条件只做并排对比表。
3. **实现方式**：纯前端确定性计算，不落后端、不落库（候选篮已是前端 Context 状态，主推/备选是只读计算）。

---

## 3. 输入与触发

- **候选篮**：复用第一 Tab 的 `CandidateContext`。
- **需求条件**：从第一 Tab 的「我要找粮」带过来，或在本 Tab 顶部再输入。
- **全部粮源**：复用 `fetchListings`（用于候选篮为空时按条件筛选）。
- 进入 Tab **自动计算展示**（只读、确定、不落库，无需「确认」按钮）。
- 本 Tab 顶部保留「我要找粮」输入框，可补充或修改需求条件。

---

## 4. 对比范围

- 候选篮非空 → 对比候选篮里的粮源。
- 候选篮空 + 有条件 → 从全部粮源按条件硬过滤后对比。
- 两者都空 → 空状态，引导「去收藏粮源」或「描述需求」。

---

## 5. 确定性对比算法（TS 纯函数）

核心函数 `compareListings(listings, need)`，输入候选粮源与需求条件，输出结构化结果。无随机，可复现。

### 5.1 硬条件过滤

需求指定了某个条件时，逐条检查；任一不满足即淘汰并记录第一个命中的原因码。需求未指定的条件不检查。

| 硬条件 | 检查 | 原因码 |
|---|---|---|
| 品种一致 | `variety_name == need.variety` | `VARIETY_MISMATCH` |
| 数量达到 | `available_quantity_tons >= need.quantity_tons` | `QUANTITY_INSUFFICIENT` |
| 等级达到 | 等级序：一等>二等>三等>四等，`grade >= need.grade` | `GRADE_BELOW_REQUIREMENT` |
| 年份符合 | `crop_year == need.crop_year` | `CROP_YEAR_MISMATCH` |
| 价格 ≤ 上限 | `price <= need.budget_price`（首版直接比数值，不折算口径） | `PRICE_OVER_BUDGET` |
| 发运不晚于 | `latest_ship_at <= need.deadline`（首版 deadline 为日期） | `SHIP_WINDOW_MISSED` |

字段缺失处理：已指定硬条件所依赖的字段缺失时（如无 `latest_ship_at` 却指定了发运期限），该粮源视为「不确定且不可入选」，记 `REQUIRED_FIELD_MISSING`。

日期基准：需求条件的 `deadline_days` 由前端相对 mock 数据基准日期（2026-08-23，与种子 `PRICE_DATE` 一致）换算为具体日期 `deadline`，不依赖运行时真实日期，保证结果可复现。

### 5.2 排序（通过硬条件后）

排序键由低到高优先：

```text
(
  required_field_missing_count,   # 关键字段缺失数（发运窗口、质检缺失）
  crop_year,                      # 年份，新粮优先（降序）
  comparable_price,               # 报价，低者前
  ship_time_penalty,              # 发运余量惩罚（越晚越靠后）
  listing_id,                     # 稳定兜底，保证可复现
)
```

第一名为主推、第二名为备选。若只有一条通过，只出主推并说明「暂无满足硬条件的备选」。

### 5.3 无结果

没有粮源通过硬条件时：不生成伪主推，逐条展示最接近的淘汰原因，并给出可操作的放宽建议（减少数量 / 放宽等级 / 延后发运 / 提高预算）。

---

## 6. 输出结构

`compareListings` 返回：

1. **需求条件摘要**：`{variety, quantity_tons, grade, deadline, budget_price}`，无需求条件时为 `null`。
2. **主推** / **备选**：`{ listing, reasons: string[], risks: string[], verification_count }`。
3. **淘汰列表**：`{ listing, reason_code, reason_text }[]`。
4. **待核验清单**：固定 5 条（见 6.4），加上字段缺失动态追加的核验项。
5. **对比表**：参与对比的全部粮源逐字段并排。

### 6.1 主推/备选卡片

展示：品种·等级·年份、产地、供应方、报价与口径、可用量、交收、发运窗口、质检摘要、入选理由、主要风险、待核验数。

### 6.2 淘汰原因

每条淘汰粮源展示原因码 + 一句确定性解释（由原因码模板生成），如：

- `QUANTITY_INSUFFICIENT` → 「可用量 100 吨，不足需求的 120 吨」。

### 6.3 逐字段对比表

列：品种·等级·年份、产地、供应方、报价（口径）、可用量、交收、发运窗口、质检摘要、状态（主推 / 备选 / 淘汰原因码）。

### 6.4 固定待核验清单

无论 Mock 数据多完整，出主推/备选时都默认给出以下交易前核验项：

1. 确认可锁定库存
2. 获取正式质检单
3. 确认报价有效期与含税口径
4. 确认装运窗口
5. 核验供应方主体与联系人

---

## 7. 明确不做

- 不接 LLM、不落库、不保存方案、不生成寻源任务（归「寻源任务」Tab）。
- 无需求条件时不硬排主推/备选。
- 不做多粮源拼单。
- 不自动联系、询价、下单、签约、付款。
- 不做不同价格口径的到厂成本折算。

---

## 8. 测试与验收

- 候选篮空 + 有条件 → 从全部粮源硬过滤，输出主推/备选可复现。
- 候选篮非空 → 只对比候选篮内的粮源，候选篮外的粮源不参与。
- 有明确条件时：满足硬条件的北安（LIANG-V1-001）成为主推、榆树（LIANG-V1-002）成为备选；铁岭（LIANG-V1-003）因等级不符淘汰、通辽（LIANG-V1-004）因数量不足淘汰。
- 无需求条件时：只展示并排对比表，不显示主推/备选/淘汰。
- 无粮源通过硬条件时：不生成伪主推，展示淘汰原因与放宽建议。
- 相同输入得到稳定结果。
- 页面不出现「演示数据 / mock」等字样。
