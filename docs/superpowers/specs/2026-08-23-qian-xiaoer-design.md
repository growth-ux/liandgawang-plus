# 钱小二｜金融产品市场与智能匹配——页面与 Agent 设计规格

> 日期：2026-08-23  
> 状态：已完成方案确认，待用户审核规格  
> 技术栈：React、FastAPI、本地 Docker MySQL、LangChain  
> 设计范围：金融市场、智能匹配、我的匹配及轻量跨小二交接

## 1. 产品定位

钱小二不是贷款申请系统，也不是企业财务驾驶舱。首版只解决两个问题：

1. 市场上有哪些适合粮贸企业的金融产品？
2. 根据当前采购和资金情况，哪个产品更适合用户，为什么？

产品定位为：

> 面向粮贸采购场景的金融产品市场与 AI 融资匹配助手。

钱小二通过可见的金融产品池、确定性的条件筛选和可解释的 AI 推荐，帮助用户减少搜索、理解和比较金融产品的时间。所有结果均为参考匹配，不代表授信、审批或放款承诺。

## 2. 需要解决的实际问题

- 金融产品分散，用户难以快速了解额度、期限、成本和担保要求。
- 产品介绍使用金融术语，用户不容易判断是否适合当前采购场景。
- 用户通常知道“缺多少钱、多久能回款”，但不知道应选择哪类融资产品。
- 低参考利率不一定代表适合，额度、期限、用途、增信方式和申请凭证可能直接导致产品不可用。
- 普通产品列表只能筛选，无法结合一笔具体粮食采购解释推荐原因。
- 纯 AI 对话看不到完整产品池，容易产生产品来源不透明或编造产品的问题。

首版成功标准：

- 用户进入页面后能直接浏览结构化金融产品市场。
- 用户能用一句自然语言描述资金需求，并快速确认 AI 提取的关键字段。
- 匹配结果稳定输出一个主推、一个至两个备选，以及代表性排除原因。
- 推荐理由能追溯到用户确认的条件和产品池中的明确字段。
- AI 不推荐产品池以外的产品，也不承诺授信或放款结果。

## 3. 首版范围

### 3.1 首版包含

- 金融产品市场浏览与筛选。
- 产品详情查看。
- 自然语言资金需求解析。
- 结构化需求确认。
- 金融产品硬条件筛选。
- 资金成本、期限和办理条件的综合比较。
- 主推、备选与不适合原因解释。
- 匹配结果保存与历史查看。
- 从粮小二、算小二接收本次任务数据。
- 将选定产品的参考资金成本交给算小二。
- 咨询金融顾问入口。

### 3.2 首版不包含

- 贷款申请、材料上传和正式提交。
- 授信审批与放款进度跟踪。
- 银行或金融机构真实系统直连。
- 企业现金流预测和财务驾驶舱。
- 贷后管理、还款提醒和逾期管理。
- 自动联系金融机构。
- 企业知识库、Mem0 或长期融资偏好记忆。
- 复杂评分模型或不可解释的匹配分数。

“咨询金融顾问”是首版最终业务动作，不得展示为申请成功、授信通过或放款完成。

## 4. 产品方案与信息架构

采用“市场 + 匹配”双核心方案：金融市场提供透明、可浏览的产品供给；智能匹配基于当前需求回答“我适合哪个”。

页面使用三个 Tab：

```text
钱小二｜找资金
├── 金融市场：市场上有什么
├── 智能匹配：我适合哪个
└── 我的匹配：以前匹配过什么
```

默认进入“金融市场”。页面主动作是“让钱小二帮我匹配”，从市场自然进入智能匹配，不采用对话欢迎页作为默认入口。

## 5. Tab 一：金融市场

### 5.1 页面目标

让用户直接看到钱小二可以使用的金融产品池，理解市场上有哪些产品、适合什么场景以及关键使用条件。

### 5.2 页面布局

采用已确认的“市场优先”布局：

```text
┌──────────────────────────────────────────────────────┐
│ 钱小二身份 / 找资金定位 / 切换小二                  │
├──────────────────────────────────────────────────────┤
│ 金融市场              智能匹配              我的匹配 │
├──────────────────────────────────────────────────────┤
│ 市场概览                        让钱小二帮我匹配     │
├───────────────┬──────────────────────────────────────┤
│ 产品筛选       │ 金融产品列表                         │
│               │ 产品卡 / 产品卡 / 产品卡             │
└───────────────┴──────────────────────────────────────┘
```

页面不常驻大型 AI 对话区，避免压缩产品市场空间。AI 入口通过顶部主按钮和产品卡中的匹配动作体现。

### 5.3 市场概览

只展示少量有决策价值的信息：

- 当前可选产品数量。
- 参考资金成本区间。
- 主要产品类型。
- 产品数据最近更新时间。
- “让钱小二帮我匹配”主按钮。

### 5.4 产品类型

首版产品池覆盖四类：

- 采购周转融资。
- 订单融资。
- 仓单或货权融资。
- 应收账款融资。

采购周转融资是首版代表性场景，其他类型用于构成完整但不过度扩张的粮贸金融市场。

### 5.5 筛选条件

首版仅保留真正影响选择的筛选项：

- 资金用途。
- 需求金额。
- 使用期限。
- 可接受的增信方式。
- 参考资金成本。

### 5.6 产品卡

每张产品卡展示：

- 产品名称和服务机构。
- 一句话适用场景。
- 额度区间。
- 可用期限。
- 参考年化成本或明确费用口径。
- 信用、保证、抵押、仓单或货权等增信方式。
- 三至五项关键准入条件。
- 产品更新时间。
- “查看详情”和“拿这个产品去匹配”。

### 5.7 产品详情

使用抽屉展示，不建设独立复杂详情页。内容包括：

- 产品适用场景。
- 额度与期限。
- 参考成本及费用说明。
- 适合与不适合的企业情况。
- 必要准入条件。
- 所需基础凭证。
- 增信方式。
- 数据更新时间和待人工确认项。

产品数据采用贴近真实业务的演示产品和稳妥的机构名称，不冒充真实银行当前在售产品。页面使用“参考成本”“需人工确认”等表达，不使用“保证授信”“必定放款”。

## 6. Tab 二：智能匹配

### 6.1 页面目标

用尽量少的输入，让用户获得稳定、透明、可以解释的金融产品推荐。

### 6.2 输入方式

支持两种入口：

1. 用户直接描述，例如：“采购200吨玉米，货款48万元，还缺30万元，预计45天回款，没有抵押物。”
2. 从粮小二或算小二带入当前采购任务的结构化数据。

跨小二数据仅用于本次匹配。首版不将其写入长期记忆，也不自动用于未来任务。

### 6.3 需求确认字段

LangChain Agent 从用户描述中提取以下字段：

- 资金用途。
- 资金缺口。
- 预计使用期限。
- 企业经营年限。
- 可接受或可提供的增信方式。
- 是否有订单、采购合同、仓单、货权或应收账款凭证。

AI 先生成“需求确认卡”，用户确认或修改后才执行匹配。没有影响匹配的字段不追问，避免形成贷款申请表。

### 6.4 匹配逻辑

匹配采用两步逻辑。

第一步为硬条件筛选：

- 需求金额是否位于产品额度区间。
- 使用期限是否位于产品期限范围。
- 资金用途是否在产品支持范围内。
- 用户可提供的增信方式是否满足要求。
- 是否具备产品明确要求的订单、合同、仓单或应收凭证。

明确不符合硬条件的产品不能进入主推或备选。

第二步为综合比较：

- 参考资金成本。
- 期限与需求的贴合程度。
- 额度与需求的贴合程度。
- 办理条件和必要凭证的完整程度。

推荐逻辑优先保证基本符合，再平衡成本、期限和办理条件。系统不展示不透明的数字匹配分。

### 6.5 参考资金成本

对于以参考年化成本表达的产品，后端按统一口径计算：

```text
参考资金成本 = 使用金额 × 参考年化成本率 × 使用天数 ÷ 365
```

若产品存在固定服务费、分段费用或无法统一计算的费用，则展示原费用口径并标记“需人工确认”，不生成虚假的精确金额。

### 6.6 匹配结果

结果页只展示：

- 一个主推产品。
- 一个至两个备选产品。
- 一个或多个代表性不适合产品及排除原因。

每个推荐产品回答：

- 为什么适合。
- 可覆盖多少资金需求。
- 参考资金成本是多少。
- 哪些条件已经满足。
- 哪些条件仍需人工确认。

可使用“高度适合”“基本适合”“条件不足”等结论，但必须紧跟具体理由。

### 6.7 页面布局

智能匹配采用已确认的单页结构，不做复杂向导：

```text
描述资金需求
→ AI 提取并展示需求确认卡
→ 用户确认
→ 同页展示主推、备选和排除原因
```

主内容区承担输入、确认和结果展示。右侧钱小二区域只解释判断和提供下一步动作，不承担主要业务操作。

结果页动作：

- 查看产品详情。
- 调整需求并重新匹配。
- 保存匹配结果。
- 咨询金融顾问。

页面固定提示：“参考匹配，不代表授信或放款承诺。”

## 7. Tab 三：我的匹配

“我的匹配”只管理历史匹配结果，不扩展为融资申请中心。

每条记录展示：

- 资金需求摘要。
- 主推产品。
- 参考成本与使用期限。
- 匹配时间。
- 当时仍需确认的条件。
- 查看结果和重新匹配入口。

重新匹配会使用旧记录生成新的需求确认卡，用户确认后再查询当前产品池。系统不直接复用旧结论，避免产品条件变化后仍展示过期推荐。

## 8. 跨小二协作

首版只实现轻量结构化交接：

### 8.1 粮小二到钱小二

可带入：

- 品种和数量。
- 采购货款。
- 付款节点。
- 采购合同或订单是否存在。
- 来源任务标识。

### 8.2 算小二到钱小二

可带入：

- 资金缺口。
- 资金占用期限。
- 可接受的参考资金成本。
- 当前测算方案标识。

### 8.3 钱小二到算小二

用户选定产品后，可交接：

- 产品名称。
- 使用金额。
- 使用期限。
- 参考年化成本或费用口径。
- 参考资金成本。
- 仍需人工确认的费用和条件。

用户确认后才发生交接。安小二可作为后续扩展，用于检查担保、费用和还款风险，首版不强制加入。

## 9. AI 与确定性规则分工

### 9.1 LangChain Agent 负责

- 理解用户自然语言需求。
- 提取资金需求字段。
- 识别真正影响匹配的缺失条件。
- 将规则匹配结果解释成通俗业务语言。
- 解释主推、备选和排除原因。
- 生成咨询金融顾问的需求摘要。

### 9.2 FastAPI 确定性服务负责

- 查询金融产品池。
- 执行额度、期限、用途和增信方式等硬筛选。
- 比较成本、期限和办理条件。
- 计算可统一口径的参考资金成本。
- 保存需求快照与匹配结果。
- 校验跨小二交接字段。

### 9.3 AI 禁止事项

- 推荐产品池以外的产品。
- 编造利率、额度、期限或准入条件。
- 修改确定性匹配结果。
- 承诺授信、审批或放款结果。
- 在用户确认前保存匹配需求或发起跨小二交接。

## 10. 简化技术架构

```text
React 钱小二页面
   ↓
FastAPI 资金服务模块
   ├── MySQL：金融产品、准入条件、匹配记录
   ├── 匹配规则：硬筛选、综合比较、成本计算
   └── LangChain：需求提取与推荐解释
```

首版不接入 Mem0。历史匹配使用普通 MySQL 记录，不从历史自动推断企业偏好。

前端建议形成独立 `qian` 功能目录；后端形成独立资金服务模块，遵循现有 `liang`、`logistics`、`analysis` 等模块的组织方式，不建设通用金融平台或复杂工作流引擎。

## 11. 核心数据对象

首版保持轻量，只需要以下业务对象。

### 11.1 金融产品

- 产品标识、名称、机构名称。
- 产品类型和适用场景。
- 最低与最高额度。
- 最短与最长期限。
- 参考年化成本和其他费用说明。
- 支持的资金用途。
- 支持或要求的增信方式。
- 必要凭证和关键准入条件。
- 数据更新时间与可用状态。

### 11.2 匹配需求

- 资金用途、资金缺口和使用期限。
- 企业经营年限。
- 可提供的增信方式和业务凭证。
- 来源类型和来源任务标识。
- 用户确认状态。

### 11.3 匹配结果

- 需求快照。
- 产品快照。
- 主推、备选或排除分类。
- 命中的条件、待确认条件和排除原因。
- 参考资金成本及费用口径。
- AI 解释文本。
- 创建时间。

保存产品快照是为了让历史记录能够还原当时的产品条件，不用于建立复杂版本系统。

## 12. 数据与演示原则

- 使用本地 MySQL 预置合理、稳定的演示金融产品。
- 不在页面醒目标注“Mock 数据”。
- 产品详情必须展示参考口径和更新时间。
- 产品名称贴近粮贸场景，机构名称不冒充真实银行当前在售服务。
- 额度、期限、成本和准入条件保持相互合理，避免一眼看出不符合金融常识。
- AI 和页面使用同一产品数据源。

建议首版准备 8 至 12 款产品，每类 2 至 3 款，足以支持筛选、匹配和排除演示，不追求大规模产品库。

## 13. 异常与边界处理

- 关键条件不足：只补问会改变筛选结果的字段。
- 没有完全匹配：展示最接近的产品和明确差距，不强行标记为主推。
- 只有一个匹配产品：只展示一个主推，不凑备选数量。
- 费用无法统一：展示产品原始费用口径并标记需人工确认。
- AI 解析失败：保留结构化字段供用户手工填写。
- 产品已停用：不能进入新匹配，历史记录仍保留当时快照。
- 跨小二数据缺失：只带入已有字段，由用户在确认卡中补充。

## 14. 视觉原则

- 延续粮达网 Plus 深蓝黑科技风。
- 使用钱小二现有暖橙色作为主强调色。
- 青绿色表达条件已满足，琥珀色表达待确认，红色只表达明确不符合。
- 金融市场首屏优先展示产品，避免做成传统银行宣传页或聊天机器人欢迎页。
- 推荐卡突出理由和条件，不用夸张收益图、金币动画或财富增长暗示。
- 桌面 Web 为竞赛演示主场景，移动端首版只保证基本可访问。

## 15. 测试重点

### 15.1 后端规则测试

- 额度、期限、用途和增信方式不符合的产品不会进入推荐。
- 相同产品池和相同需求产生稳定的结构化匹配结果。
- 参考资金成本公式计算正确。
- 无完全匹配时返回差距说明，不伪造主推。
- 产品停用后不参与新匹配。

### 15.2 Agent 测试

- 从典型粮贸描述中正确提取金额、期限、用途和增信条件。
- 缺少关键字段时只提出必要问题。
- 解释内容只能引用结构化匹配结果和产品数据。
- 不生成产品池以外的产品、成本或授信承诺。

### 15.3 前端流程测试

- 金融市场筛选、产品详情和匹配入口可用。
- 需求确认前不执行正式匹配。
- 主推、备选和排除原因展示清楚。
- 保存后能在“我的匹配”查看需求与产品快照。
- 从粮小二或算小二进入时能正确展示带入字段。

## 16. 竞赛演示场景

代表场景：

> 某饲料企业计划采购200吨玉米，采购货款约48万元，当前资金缺口30万元，预计45天后回款，没有抵押物，但有采购合同。

演示流程：

```text
进入钱小二查看金融市场
→ 浏览采购周转、订单、仓单和应收融资产品
→ 输入一句话资金需求
→ AI 提取并让用户确认关键条件
→ 规则从产品池中筛选
→ 输出一个主推、一个备选和仓单融资的排除原因
→ AI 解释成本、期限与办理条件的取舍
→ 用户查看主推产品或发起金融顾问咨询
```

该场景能够同时证明产品市场可见、AI 理解需求、匹配结果可解释，以及钱小二能够解决实际粮贸采购资金选择问题。
